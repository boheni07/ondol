## 목적

구현된 기능을 사용자와 팀이 이해할 수 있는 텍스트로 정리한다. 없는 기능을 서술하지 않고, 실제 동작 기준으로 작성한다.

## 작업 순서

### 1단계: 독자와 문서 타입 확인

| 문서 타입 | 독자 | 위치 |
|---------|------|------|
| README | 개발자/기여자 | 프로젝트 루트 |
| API 문서 | 프론트엔드 개발자 | `docs/api.md` |
| 사용자 가이드 | 서비스 사용자 | `docs/guide.md` |
| 릴리스 노트 | 팀/사용자 | `docs/changelog.md` |

### 2단계: 소스 확인
- QA 통과 여부 확인: `_workspace/03_qa_review.md` 에 PASS가 있는지
- 구현 코드와 설계 문서를 직접 읽고 사실 기반으로 작성

### 3단계: 초안 작성

`_workspace/04_documenter_draft.md` 에 초안 작성 후 최종본을 `docs/` 에 저장.

**README 기본 구조:**
```markdown
# {프로젝트명}

{한 줄 설명}

## 기능
- {주요 기능 목록}

## 시작하기
{설치 및 실행 방법}

## 기술 스택
{사용된 기술}

## 환경 설정
{필요한 환경변수}
```

**API 문서 기본 구조:**
```markdown
# API 레퍼런스

## {엔드포인트명}
`{METHOD} {path}`

**요청:**
```json
{요청 body 예시}
```
**응답:**
```json
{응답 예시}
```
```

### 4단계: 작성 원칙

- 같은 내용은 한 번만 쓴다 — 반복 대신 참조
- 코드 예시는 실제 동작하는 것만 포함
- 버전/날짜 정보는 자동화되지 않은 곳에서는 명시적으로 표기

### 5단계: 오케스트레이터에 완료 보고

문서 작성 완료 후 저장된 파일 경로 목록을 보고한다.
