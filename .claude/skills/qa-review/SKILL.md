## 목적

구현 코드가 요구사항을 충족하는지 확인하고, 숨겨진 버그와 경계면 오류를 발견한다. 파일 존재 확인이 아닌 실제 로직의 정합성 검증이 핵심이다.

## 작업 순서

### 1단계: 검증 기준 수집
- `_workspace/01_analyst_requirements.md` — 원본 요구사항
- `_workspace/02_architect_design.md` — 설계 의도
- 검증할 구현 코드 파일 목록 확인

### 2단계: 경계면 교차 검증

단순 파일 존재 확인이 아니라 경계를 가로지르는 검증을 수행한다:

| 경계 | 검증 내용 |
|-----|---------|
| API ↔ 프론트엔드 | 응답 shape이 프론트 타입 정의와 일치하는가? |
| DB ↔ API | 쿼리 결과가 API 응답 스키마와 일치하는가? |
| 요구사항 ↔ 구현 | 모든 성공 기준이 코드로 구현되었는가? |
| 인증 ↔ 권한 | 인증 없이 접근 가능한 경로가 없는가? |

### 3단계: 체크리스트 실행

**기능 검증:**
- [ ] 모든 요구사항 항목이 구현에 반영되었는가?
- [ ] 엣지 케이스 처리 (빈 값, 최대값, 동시 요청)
- [ ] 에러 응답이 사용자에게 적절히 전달되는가?

**코드 품질:**
- [ ] 하드코딩된 값 없음 (환경변수 사용)
- [ ] SQL Injection, XSS, CSRF 취약점 없음
- [ ] 민감 정보 로그 출력 없음

**성능:**
- [ ] N+1 쿼리 없음
- [ ] 불필요한 전체 데이터 로드 없음

### 4단계: 결과 작성

`_workspace/03_qa_review.md` 에 작성:

```markdown
# QA 리뷰 — {기능명}

## 결과: PASS / FAIL

## 통과 항목
- {항목}: 확인 완료

## 발견 이슈
| 심각도 | 파일 | 라인 | 내용 | 수정 방향 |
|--------|------|------|------|---------|

## 개선 제안 (선택)
- {PASS지만 개선하면 좋은 것}
```

### 5단계: 결과 전달
- FAIL이면: architect-developer에게 이슈 목록 SendMessage
- PASS이면: 오케스트레이터에 통과 보고, documenter에 문서화 시작 알림
