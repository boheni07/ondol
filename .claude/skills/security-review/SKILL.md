## 목적

구현이 안전한지 검증한다. 기능이 요구사항대로 동작하더라도 권한 우회, RLS 갭, 데이터 노출이 있으면 배포할 수 없다. "안전한가"를 기능 정합성과 분리해 본다.

## 작업 순서

### 1단계: 검토 기준 수집
- `docs/13-rls-policy.md` — 테이블별 RLS 정책·access_level 규칙
- `docs/12-api-index.md` — API 경로·인증 요구
- `_workspace/02_architect_design.md` — DB 스키마·인증 설계
- 구현 코드, Supabase 마이그레이션·정책 파일

### 2단계: RLS 정책 교차 검증

| 검증 | 내용 |
|-----|-----|
| 정책 커버리지 | 모든 테이블에 RLS가 켜져 있고 정책이 정의되었는가? |
| 정책 ↔ 문서 | 실제 정책이 docs/13과 일치하는가? |
| 우회 경로 | service_role·익명 키로 정책을 우회할 수 있는가? |
| access_level | read/write/edit/admin이 정책으로 강제되는가? |
| admin 위임 | admin이 주보호자 전용·위임 불가로 보장되는가? |

### 3단계: OWASP Top 10 점검
- [ ] 접근 제어 결함 (수직/수평 권한 상승)
- [ ] 인증 실패 (세션·토큰·비밀번호 정책)
- [ ] 인젝션 (SQL·NoSQL·명령)
- [ ] 민감 데이터 노출 (전송/저장 암호화)
- [ ] SSRF·보안 설정 오류

### 4단계: 개인정보(PII)·시크릿
- [ ] PII 수집·저장·전송·로그 출력 전 구간 보호
- [ ] 하드코딩된 키·토큰 없음
- [ ] 클라이언트 번들에 서버 시크릿 노출 없음
- [ ] `.env` 커밋 여부, 환경변수 분리

### 5단계: 결과 작성

`_workspace/03b_security_review.md` 에 작성:

```markdown
# 보안 검토 — {기능명}

## 결과: PASS / FAIL (Critical 존재 시 FAIL)

## 발견 사항
| 등급 | 영역 | 파일/정책 | 내용 | 수정 방향 |
|------|------|----------|------|---------|
| Critical/High/Medium/Low | RLS/Auth/PII/Secret | ... | ... | ... |

## RLS 갭 (문서 대비)
- {테이블}: docs/13 정책 vs 구현 차이

## 차단(blocking) 이슈
- {배포 전 반드시 수정할 항목}
```

### 6단계: 결과 전달
- Critical/High: architect-developer에게 SendMessage, 오케스트레이터에 차단 보고
- RLS 갭: data-infra에 마이그레이션 수정 협의
- 상충 데이터는 삭제하지 않고 출처(문서 vs 코드) 병기
