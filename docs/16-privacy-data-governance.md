# 개인정보·데이터 거버넌스 정책 — OnDol 플랫폼

> 버전: v1.0 (초안) | 작성일: 2026-06-14
> 기준 법령: 「개인정보 보호법」(이하 PIPA) 및 같은 법 시행령 | DB: PostgreSQL (Supabase) | 타임존: KST (UTC+9)

본 문서는 OnDol이 수집·처리하는 개인정보(특히 미성년자·피후견인의 **건강·장애 정보**)의 거버넌스 정책을 규정한다.
`docs/13-rls-policy.md`가 **DB 행 수준 접근통제(RLS)** 를 다룬다면, 본 문서는 그 상위의 **수집·동의·보관·파기·권리행사·위탁** 등 데이터 라이프사이클 거버넌스를 다룬다. 두 문서는 §8(안전성 확보조치)에서 연계된다.

> ⚠️ **법무 검토 전 초안**: 본 문서의 보유기간 등 법정 수치는 모두 "권장/검토 필요"로 표기했으며, 단정적 수치는 사용하지 않았다. 법무 확정이 필요한 항목은 모두 §9 TBD에 모았다. 본 문서는 `docs/02-data-specification.md`(§2 테이블·§3 JSONB·§4 Enum)와 `docs/13-rls-policy.md`에 **정의된 데이터 구조에 근거**하며, 추측한 정책은 🟡로 표기한다.

## 2. 동의 체계

### 2.1 필수 / 선택 동의 분리 (PIPA §22)

| 동의 항목 | 구분 | 대상 |
|----------|:----:|------|
| 서비스 이용약관 | **필수** | 전체 가입자 |
| 개인정보 수집·이용(필수 항목) | **필수** | 전체 |
| **민감정보(장애·건강) 수집·이용** | **별도 필수** (§3) | 당사자 등록 시 |
| **고유식별정보(장애등록번호 등)** | **별도 필수** (§3) | 해당 기록 입력 시 |
| 제3자 제공/처리위탁 고지 | **고지·동의** | 전체 (§6) |
| 마케팅·부가서비스 알림 | **선택** | 동의자 한정 |

> 필수 동의를 선택 동의와 묶어 일괄 동의받는 것은 PIPA §22⑤ 위반이다. 각 동의는 **분리된 체크박스**로 받는다(UI는 `docs/05 §1` 온보딩 흐름에 동의 단계 삽입 필요 🟡 — 현재 워크플로우에 명시적 동의 노드 부재).

### 2.2 법정대리인 대리동의 (PIPA §22-2 / §39-3)

OnDol의 **당사자(person)는 미성년자 또는 피후견인**이 대부분이므로, 당사자 개인정보의 수집·이용 동의는 원칙적으로 **법정대리인이 대리**한다.

| 당사자 상태 | 동의 주체 | 시스템 매핑 |
|------------|----------|-----------|
| 만 14세 미만 아동 | **법정대리인(친권자)** | `guardian_persons.is_primary=true` 보호자 (docs/02 §2.3) |
| 만 14세 이상 미성년자 | 본인 + (필요 시) 법정대리인 🟡 | docs/05 §1 온보딩 — 연령 분기 미구현 |
| 피성년후견인 | **성년후견인** | `guardian_persons.relationship='후견인'` + LEG-003 (docs/02 §3.F) |
| 의사결정지원 대상 | 본인 + 지원자 | TRA-006/LEG-004 (docs/02 §3.E·F) — 본인 의사 우선 |

- 법정대리인 자격은 가입 시 `guardian_persons` 연결로 표현되며, **주보호자(`is_primary`)** 가 대리동의·권한 관리의 주체다(docs/13 §3.3 `is_primary_guardian`).
- 🟡 **검토 필요**: 법정대리인 자격 증빙(가족관계증명서·후견등기사항증명서) 확인 절차는 현재 설계에 없다. PIPA §22-2는 만 14세 미만 시 법정대리인 동의·확인을 요구한다.

#### 2.2.1 만 14세 이상 미성년자 동의 분기 권고안 (🟡 확정 필요)

> docs/05 §1-3 F3 노드("만 14세 이상 미성년자 → 본인 + 법정대리인 확인 🟡")의 구체 흐름 권고. PIPA §22-2는 만 14세 *미만*에 법정대리인 동의를 요구한다. 만 14세 *이상* 미성년자는 법상 본인 동의 가능 여지가 있으나, OnDol은 **민감정보(건강·장애)** 를 처리하고 계약 주체가 미성년자라는 특수성이 있어 보강 흐름을 권고한다.

- **권고(UI 상태 흐름):**
  1. 본인이 `privacy_required`·`sensitive_info` 동의 체크 → `consents`에 `subject_user_id=본인`, `on_behalf=false`, `granted=true` INSERT.
  2. 동시에 법정대리인 확인 단계로 전이(상태: `awaiting_guardian_confirmation`) — 본인 동의만으로는 당사자 등록·민감정보 저장을 **완료하지 않고 보류**.
  3. 법정대리인이 별도 채널(앱 내 보호자 계정 또는 인증 링크)에서 확인 → `consents`에 동일 대상 `on_behalf=true`, `legal_basis='친권자'`, `consented_by=법정대리인` 보조 레코드 INSERT.
  4. 두 레코드(본인 `granted=true` + 법정대리인 확인)가 모두 존재할 때 상태 `confirmed` → 민감정보 저장 활성화.
- **근거:** PIPA §22-2(연령 분기) + 민감정보 별도 동의(§3.1). 본인 의사 우선(의사결정지원 원칙, TRA-006)을 살리되 미성년 계약·민감정보 처리의 법적 안정성을 위해 법정대리인 확인을 병행한다. 본인+대리인 *이중* 레코드 구조는 docs/02 §2.15 `consents`(subject_user_id / on_behalf)로 표현 가능.
- **확정 주체:** 법무(만 14세 이상 미성년자 민감정보 처리 시 본인 단독 동의 가능 여부·법정대리인 확인 필수 여부) · architect(상태머신 구현).
- 🔒 **보안 위험:** 법정대리인 확인 채널(인증 링크)이 검증 없이 열리면 제3자가 미성년자 민감정보 등록을 승인할 수 있다 — 링크 만료·본인확인 결합 필요(권한 우회 위험).

#### 2.2.2 법정대리인 자격 증빙 절차 권고안 (🟡 확정 필요)

> §9 #8. 가족관계·후견 자격을 어떻게 증빙·검증·보관할지 권고.

| 자격 유형 | 증빙 수단(권고) | 검증 시점 | 검증 방식(권고) |
|----------|----------------|----------|----------------|
| 친권자(만 14세 미만 아동) | 가족관계증명서(상세) | 당사자 최초 등록 시 + 민감정보 동의 전 | 1차: 서류 업로드 후 운영자 수기 검토 / 2차(차기): 공공 마이데이터·전자가족관계등록 API 연계 🟡 |
| 성년후견인 | 후견등기사항증명서 | 후견 개시 등록 시(LEG-003) | 동일 — 후견 범위(신상·재산) 확인 |
| 임의후견·의사결정지원자 | 후견계약 공정증서·지원 계약서 | 지원 관계 등록 시(LEG-004/TRA-006) | 본인 의사 확인 병행 |

- **권고(보관·처리):** 증빙 서류 **이미지/PDF는 그 자체가 민감·개인정보**이므로 `record_files`(`is_sensitive=true`) 또는 전용 검증 스토리지에 저장하고, **검증 완료 후에는 결과 플래그만 유지하고 원본은 최소 보유기간 후 파기**하는 것을 권고(원본 장기보관 지양). `consents.legal_basis`에는 검증 결과(친권자/성년후견인)만 텍스트로 남긴다.
- **근거:** PIPA §22-2(법정대리인 동의·확인 의무) + §3②(수집 최소화) + §23/§24(서류 내 민감·고유식별정보 보호). 증빙 *결과*만 영속 보관하고 *원본*은 단기 보관해 위험을 줄인다.
- **확정 주체:** 법무(요구 증빙 수단·법정 확인 수준) · architect(검증 워크플로우) · 인프라(검증 스토리지·파기 배치).
- 🔒 **보안 위험:** 증빙 서류(가족관계증명서·후견등기)는 주민번호 등 고유식별정보를 포함할 수 있어, 원본 장기 보관 시 단일 유출로 가족 전체 PII가 노출된다 — 검증 후 원본 즉시 파기 또는 암호화 격리 필요(증빙서류 PII 위험).

### 2.3 당사자 전환기(성년 도달) 동의 재취득

당사자가 성년에 도달하면 법정대리인 대리동의의 법적 근거가 변동되므로 **본인 동의 재취득**이 필요하다. `docs/05 §10 당사자 전환기 처리`의 생애주기 전환 흐름과 연계한다.

| 전환 시점 | 트리거(docs/05 §10) | 동의 거버넌스 조치 |
|----------|---------------------|-------------------|
| **청소년→성인전환기 (19세)** | docs/05 §10 `F2` 노드(법적 서류 검토 알림) | 후견 여부 확정(LEG-003) → 후견 미개시 시 **본인 동의 재취득 절차 개시** 🟡 |
| 성년 도달·후견 미개시 | — | 당사자 본인이 직접 동의 주체로 전환, `person_accounts.user_id` 연결 (docs/02 §2.4) |

- docs/05 §10에 **성년 전환 시 본인 동의 재취득 흐름**이 추가되었다(✅ 정합화 2026-06-14). 생애주기 단계(`persons.current_life_stage`) 갱신·권한 연장과 함께 후견 미개시 시 본인 동의를 재취득한다.

## 3. 민감정보·고유식별정보 별도 동의 처리

### 3.1 민감정보 (PIPA §23)

- **대상**: §1.2의 🟥 항목 — 장애 유형·정도(`persons.disability_types`), 응급 의료정보(`persons.emergency_info`), 의료기록(`records` domain=`medical`), 자기표현(`self_expressions`), 민감 첨부파일(`record_files.is_sensitive=true`).
- **원칙**: 다른 동의와 **분리된 별도 동의**를 받아야 한다(PIPA §23①). 동의 없는 민감정보 처리는 금지.
- **시스템 연계**: 민감 파일은 `record_files.is_sensitive=true`로 분류되어 presigned URL(5분 유효) + 권한 재검증으로 접근 통제된다(docs/05 §11-2, docs/13 §2 `record_files` 행).

### 3.2 고유식별정보 (PIPA §24)

- **대상**: §1.2의 🟧 항목 — 장애인 등록번호(WEL-001 `registration_number`), 장애인 증명서 문서번호(LEG-001 `document_number`).
- **원칙**: 별도 동의 + **암호화 저장 의무**(PIPA §24③, 시행령 §21).
- **현 설계 상태**: ✅ **구조 확정**(정합화 2026-06-14) — 두 항목을 JSONB content 평문에서 분리해 docs/02 §2.14 `secure_identifiers` 테이블(`encrypted_value` 암호화 저장 + `value_masked` 표시용)로 이관했다. **마스킹(표시)≠암호화(저장)** 역할이 모델에서 분리되었다.
- **권고**: 고유식별정보는 가능한 한 **수집하지 않거나**(서비스상 불필요 시), 수집이 불가피하면 위 분리 저장 구조를 따른다.

> 🟡 잔여(§9 #2): 암호화 **도구·키관리** 선택(Supabase Vault vs pgcrypto+KMS)은 data-infra·법무 확정 대상. 구조(분리 저장)는 확정됨.

#### 3.2.1 암호화 도구·키관리 권고안 (🟡 확정 필요)

> Supabase 직접 제어 환경(docs/10 §3.1)을 전제로 두 후보를 비교한다. **본 절은 권고이며 결정이 아니다.**

| 항목 | A. Supabase Vault | B. pgcrypto(`pgp_sym_encrypt`) + 외부 KMS |
|------|-------------------|------------------------------------------|
| 키 보관 | Vault가 키를 자체 관리(`vault.secrets`), DB와 분리된 시크릿 | KMS(예: AWS KMS·GCP KMS)에 마스터키, DB는 데이터키만 사용 |
| 암복호 위치 | DB 내장 함수(`vault.decrypted_secrets`) | 앱/Edge Function에서 KMS로 데이터키 복호 후 pgcrypto 호출 |
| 키 회전 | Vault 키 회전 기능 의존(성숙도 검증 필요 🟡) | KMS 자동 회전 + 데이터키 봉투암호화(envelope)로 표준화 용이 |
| 운영 복잡도 | 낮음(Supabase 통합) | 높음(KMS 연동·IAM·네트워크) |
| 키-데이터 분리 | 동일 Supabase 경계 내 | **물리적 분리**(KMS 별도 신뢰경계) — PIPA §24③ 취지 부합도 높음 |

- **권고:** 1차 출시는 **A. Supabase Vault**로 시작하되(운영 단순·통합), 고유식별정보 규모·감사 요구가 커지면 **B. pgcrypto+KMS(봉투암호화)** 로 전환 가능한 추상화 계층(`encryption_ref`로 키 식별, docs/02 §2.14)을 둔다.
- **근거:** docs/10 §3.1은 Supabase 직접 제어를 확정했고 Vault는 추가 인프라 없이 키-데이터 논리 분리를 제공한다. 단 키-데이터 *물리* 분리·자동 회전 성숙도는 외부 KMS가 우위라 장기적으로 B를 옵션으로 남긴다.
- **키 회전·접근통제 방향(권고):** ①키는 최소 연 1회 또는 유출 의심 시 즉시 회전, `encryption_ref`에 키 버전 기록(과거 버전 복호 가능하도록 보존) ②복호 함수(`decrypt_secure_identifier`)는 `service_role`/Edge Function 한정 EXECUTE, `authenticated` 미부여(docs/13 §3.5) ③복호 1건마다 `access_logs`에 `action='decrypt'` 기록(누가·언제·어느 식별정보) ④키 자체는 `.env`·코드·클라이언트 번들에 절대 미포함(docs/10 §7).
- **확정 주체:** 인프라(도구·KMS 연동·키 회전 주기) · 법무(PIPA §24③·시행령 §21 충족 여부 최종 확인).
- 🔒 **보안 위험:** Vault/KMS 키가 `service_role` 키와 함께 유출되면 분리 저장의 의미가 소멸 — 키 접근 경로와 `service_role` 키 보관을 별도 신뢰경계로 격리해야 한다(키 노출 위험).

#### 4.1.1 항목별 보유기간 권고안 (🟡 확정 필요 — 법무)

> 아래는 **법령 근거를 병기한 권고 범위**다. 단정 수치가 아니며 법무가 적용 법령·해석을 최종 확정한다. 의료·복지 영역은 OnDol이 의료기관/복지시설이 아니라 **이용자가 자기 기록을 보관하는 플랫폼**이라는 점에서 해당 영역법 보존의무의 직접 수범자가 아닐 수 있으므로, "근거가 될 수 있는 법령"으로 제시한다.

| 데이터군 | 권고 보유기간(범위) | 근거가 될 수 있는 법령(검토 필요) | 확정 주체 |
|---------|--------------------|----------------------------------|----------|
| 계정·프로필(`users`/`persons`/`person_accounts`) | 탈퇴 시까지 → 탈퇴 후 **즉시~5일 내** 파기 | PIPA §21①(목적 달성 시 지체 없이 파기) | 법무 |
| **접속·접근 기록**(`access_logs`) | **권고 1년**(범위 6개월~3년) | 통신비밀보호법·정보통신망법상 접속기록 보관 관행, PIPA 시행령 §30(접속기록 1년 이상 보관·점검 — 5만명 이상/민감정보 처리자 **2년 이상**) | 법무 |
| **권한 변경 이력**(`permission_logs`) | **권고 1~2년** | 위와 동일(감사·분쟁 대응) + PIPA §29 안전성 확보 | 법무 |
| **동의 이력**(`consents`) | **계약 종료 후 권고 5년** | 전자상거래법 §6(계약·청약철회 기록 5년) 유추 + 동의 입증책임(PIPA §22) 대비 | 법무 |
| **고유식별정보**(`secure_identifiers`) | 수집목적 종료/철회 시 **즉시 파기**(최소 보유) | PIPA §21①·§24(수집 최소화·목적 한정) | 법무 |
| 생애 기록 본문(`records`/`self_expressions`/`life_milestones`) | 보유목적 존속 기간(이용자 보관 의사 존중) — 별도 동의·보관 근거 명시 | PIPA §21①, 별도 보관 동의 시 §15①7 | 법무 |
| 알림(`notifications`) | **권고 90일** 후 파기 | 서비스 목적 한정(PIPA §3②) | PM·법무 |

- **권고:** 접속기록은 **PIPA 시행령 §30 기준 1년**을 기본값으로 하되, OnDol이 **민감정보(건강·장애)를 처리**하므로 동 조항의 강화 기준(**2년 이상**) 적용 여부를 법무가 우선 판단한다.
- **근거:** PIPA 시행령 §30①3은 개인정보처리자에게 접속기록 1년 이상(민감정보·고유식별정보 처리 시 2년 이상) 보관·점검을 요구한다. OnDol은 §1.2 기준 민감정보·고유식별정보를 처리하므로 **2년 기준이 적용될 가능성**이 있다.
- **확정 주체:** 법무(법령 적용·해석·수치 확정), 인프라(파기 배치 주기 구현 — §4.3·docs/13 §4).
- 🔒 **보안 위험:** 접속/권한 로그를 법정 기준보다 **과다 보유**하면 그 자체가 PII·행동패턴 축적으로 유출 시 피해가 확대된다 — 보유기간 경과분은 §4.3 service_role 배치로 반드시 파기(로그 과보유 위험).

### 4.2 파기 트리거

| 트리거 | 대상 | 처리 |
|--------|------|------|
| **회원 탈퇴** | 탈퇴자 본인 데이터 | soft delete → 유예기간 후 hard delete (§4.3) |
| **당사자 삭제** | 해당 `person_id`의 전 기록 | CASCADE 검토 🟡 (FK 정책 docs 미정) |
| **권한 회수/만료** | `permissions` 행 | `is_active=false`(docs/05 §3) — 행 파기 아님, 로그 보존 |
| **보유목적 달성** | 목적 종료 데이터군 | 정기 파기 배치 🟡 |
| 동의 철회(§5) | 철회 범위 데이터 | 처리정지 또는 파기 |

### 4.3 파기 방식 & append-only 로그 충돌 처리

| 데이터 유형 | 파기 방식 |
|------------|----------|
| 일반 기록(`records`, `self_expressions` 등) | **soft delete**(논리 삭제 플래그) → 유예기간 경과 후 **hard delete**(물리 삭제) 🟡 (현 스키마에 deleted_at 컬럼 부재 — 보강 필요) |
| 첨부 파일 | Storage 객체 hard delete + `record_files` 행 삭제 |
| **`access_logs` / `permission_logs`** | **불변(append-only)** — docs/13 §4에 따라 UPDATE/DELETE RLS 정책 미생성으로 차단됨 |

> ⚠️ **충돌 지점**: docs/13 §4는 두 로그 테이블을 **불변(파기 불가)** 로 규정한다. 그러나 PIPA §21은 보유기간 경과 시 파기를 요구한다. 이는 **상충**한다.
> - **해소 방향(권장)**: 로그를 영구 보존하지 않고 **보유기간 경과분을 시스템 권한(서비스 롤)으로 일괄 파기**하되, RLS는 일반 사용자의 변조를 계속 차단한다(불변성=사용자 변조 방지, 파기=시스템 배치). 즉 "사용자에 대한 불변"과 "법정 보유기간 후 시스템 파기"를 분리한다.
> - 구체 구현(파티션 드롭 / service_role 삭제 배치 / 보유기간 값)은 §9 TBD이며 data-infra·법무 협의 대상이다.

| 거부 통지 | 거부 시 사유·이의제기 방법 서면(앱 내·이메일) 통지 양식 |
| 기록 | 권리행사 접수·처리 내역을 `access_logs` 또는 별도 이력에 기록(이행 입증) |

- **권고:** 권리 유형별 라우팅(열람→타임라인/로그 조회, 삭제→soft-delete 트리거, 전송요구→기록 export(§5.1 #5·§9 #9))을 단일 창구에서 분기.
- **근거:** PIPA §35~37·시행령 §41. 본인확인 강화는 권리행사 사칭으로 인한 정보 탈취 방지.
- **확정 주체:** 법무(SLA 일수·거부 사유 양식) · architect(창구·라우팅 구현).
- 🔒 **보안 위험:** 본인확인이 약하면 권리행사 창구가 **계정 탈취·타인 정보 열람** 경로가 된다 — 민감 권리는 재인증 필수(사칭 열람 위험).

## 6. 제3자 제공 / 처리위탁 (PIPA §17·§26·§28-8)

### 6.1 처리위탁 현황 (수탁사)

| 수탁사 | 위탁 업무 | 처리 데이터 | 국외이전 | 근거(docs/10) |

| **Resend** | 이메일 발송(초대·알림) | 이메일 주소, 알림 제목·본문 | **예** (해외 서비스) 🟡 | docs/10 §4 |

| Sentry | 에러 추적 | 에러 컨텍스트(PII 포함 위험) 🟡 | **예** 🟡 | docs/10 §6 |

### 6.2 핵심 검토 사항

- **제3자 제공(§17)** 은 현재 설계상 없음 — 데이터는 위탁(§26) 처리만 발생(서비스 운영 목적). 향후 통계·연구 제공 시 별도 동의 필요.
- **국외이전(§28-8)**: Supabase·Resend·Vercel·FCM·Sentry는 해외 인프라 가능성이 높다. 국외이전 시 **이전받는 자·국가·항목·시점·방법·목적을 고지하고 동의**받아야 한다. → **리전 확정 + 처리방침 고지** 필수(§9 TBD).
- **Sentry PII 누출 위험** 🟡: 에러 페이로드에 `persons.emergency_info`·`records.content` 등 민감정보가 섞일 수 있다. **민감 필드 스크러빙(beforeSend 마스킹)** 설정을 §8과 연계해 강제해야 한다.
- 수탁사별 **위탁계약서(DPA)·재위탁 통제** 확인 필요.

### 8.2 접근기록(감사 로그) 연계

- 모든 view/create/edit/delete/download/share/permission_change 행위는 `access_logs`에 INSERT(불변). 보호자가 투명성 차원에서 조회 가능(docs/13 §3.4, docs/05 §9).
- 권한 변경은 `permission_logs`에 트리거로 자동 기록(docs/13 §4).
- **권한 외 접근 시도 감지** → 보호자 알림(docs/13 §5, WBS 4.4).
