# 테스트 전략 — OnDol 플랫폼

> 버전: v1.0 | 작성일: 2026-06-14

OnDol(장애 생애주기 기록 B2C 서비스, Next.js + Supabase)의 **테스트 SSOT(Single Source of Truth)** 문서다. 그간 테스트 기준이 WBS(`docs/08-wbs-v1.1.md`)의 `🧪 테스트 전략` 노트와 접근성 체크리스트(`docs/14`)·RLS 정책(`docs/13`)에 분산되어 있었던 것을 단일 전략으로 통합한다.

본 문서는 `docs/10-tech-stack.md §5`에 **이미 선정된 테스트 스택만** 사용한다. 미선정 영역은 후보를 제시하되 🟡 **TBD(선정 필요)**로 표기하며, 새 도구를 임의 추가하지 않는다. 참조는 `docs/NN §X` 형식을 따른다.

> 표기: ✅=확정·운영 · ⚪=차기(P1) · 🟡=TBD(선정/정의 필요)

## 1. 전략 개요 & 원칙

### 1-1. 핵심 원칙 (WBS v1.1 테스트 내재화)

OnDol은 `docs/08 v1.1`에서 **단위→통합→E2E 테스트가 구현과 함께 내재화**되도록 구현 순서를 재정렬했다(`docs/08 §V1.1 구현 순서`). 본 전략은 이 원칙을 그대로 계승한다.

- **P1. 테스트 먼저 깔기** — 코드 작성 전 Phase 0에서 테스트 인프라(Vitest·Playwright·pgTAP)와 CI 파이프라인을 먼저 구축한다(`docs/08 0.13·0.14`). 이후 **모든 Phase에서 단위 테스트를 구현과 동시에 작성**하는 것을 팀 원칙으로 한다(`docs/08 §0 Phase 헤더`).
- **P2. 테스트 없는 머지 금지** — 마이그레이션은 pgTAP, API는 Vitest+Supertest, 화면은 Storybook 스냅샷/axe-core 검사를 동반해야 머지한다(`docs/08 §1·§2 Phase 헤더`).
- **P3. 보안·권한은 이중 검증** — RLS 권한은 **pgTAP(정책 레벨)** + **Supertest(엔드포인트 레벨)**로 이중 검증한다(`docs/08 §4 Phase 헤더`).
- **P4. 경계면 교차 검증** — API 스펙(`docs/12`)과 프론트 연동부의 데이터 shape 불일치를 통합 단계에서 잡는다(§7).
- **P5. 체크포인트 게이트** — 백엔드(Phase 5~11) 완료 시점에 통합 검증 체크포인트(`docs/08 §11.5`)를 통과해야 프론트엔드(Phase 12)로 진입한다.

### 1-2. 테스트 피라미드

```
            ▲  E2E (Playwright 웹 / Detox 모바일)
           ╱ ╲   5개 핵심 플로우 + 역할별 — 느림·고비용 — 야간 회귀
          ╱   ╲
         ╱ 통합 ╲  Supertest(API↔DB) + pgTAP(RLS) — 실 Supabase 연동
        ╱       ╲
       ╱  단위    ╲  Vitest(웹/공유) · Jest(모바일 RN) — 빠름·다수 — PR마다
      ╱___________╲
```

| 레벨 | 비중(권장) | 도구 | 실행 시점 | 근거 |
|------|:---:|------|---------|------|
| 단위 | 약 60~70% | Vitest·Jest(RN) | PR마다 | `docs/10 §5`, `docs/08 18.1.1` |
| 통합 | 약 20~30% | Supertest·pgTAP | PR마다(DB)·머지 전 | `docs/10 §5`, `docs/08 18.1.2·18.1.4` |
| E2E | 약 5~10% | Playwright·Detox | 야간 회귀·릴리스 전 | `docs/10 §5`, `docs/08 18.1.3·16.x` |

> 비중은 작업 수·실행 빈도 기준 권장치다. 단위 커버리지 목표는 §3에서 정량화한다.

### 1-3. 무엇을 어느 레벨에서 검증하는가

| 검증 대상 | 레벨 | 근거 |
|----------|------|------|

## 2. 레벨별 전략

### 2-1. 단위 테스트 — Vitest(웹/공유) · Jest(모바일 RN) ✅

- **도구:** Vitest(`docs/10 §5`, `docs/08 18.1.1`). 모바일 RN은 Jest(`docs/08 §16 Phase 헤더 "Detox E2E + Jest"`).
- **대상:** 순수 로직 — RHF+Zod 검증(`docs/10 §1`), 분기 처리, 토큰 생성/만료(`docs/08 2.4·2.7`), env 검증 유틸(`docs/08 0.5`), 접근성 토큰 대비 계산(`docs/08 12.1.4·17.3.3`), 생애주기 경계값(`docs/08 3.2.9`는 트리거이므로 pgTAP, 클라이언트 계산 로직은 단위).
- **외부 의존성:** Supabase 클라이언트·Resend·OAuth·FCM·TTS는 모킹한다(`docs/08 0.6·2.4·2.10·17.3.4`).
- **컴포넌트:** Phase 12 모든 컴포넌트는 **Storybook 스토리 + 렌더 스냅샷**을 동반한다(`docs/08 §12 Phase 헤더`).

### 2-2. 통합 테스트 (API ↔ DB) — Supertest ✅

- **도구:** Supertest(`docs/10 §5`, `docs/08 18.1.2`).
- **대상:** `docs/12 API 인덱스`의 HTTP 엔드포인트. 요청/응답·상태코드(예: 401/403)·CRUD가 RLS와 함께 올바르게 동작하는지 **실 Supabase 연동**으로 검증한다(`docs/08 §3 Phase 헤더`).
- **필수 케이스 패턴:** 성공 / 무권한 차단 / 만료·위조 토큰 / 본인 vs 타인 / 중복·제약 위반. (WBS 각 API 프롬프트가 케이스를 명시 — 예: `docs/08 2.9` 신규·기존·만료·위조 4케이스, `docs/08 4.1.1` 부여·admin 위임 차단·중복 UPSERT.)
- **경계:** DB 트리거·scheduled fn·edge function 등 비-HTTP 산출물(`docs/12 부록`)은 엔드포인트 통합 대신 그 효과(예: `permission_logs` 자동 기록)를 통합/ pgTAP로 검증한다.

### 2-3. E2E 테스트 — Playwright(웹) ✅ · Detox(모바일) 🟡

- **웹:** Playwright(`docs/10 §5`, `docs/08 18.1.3`). 5개 핵심 플로우(§4) + 역할별 플로우(`docs/08 §15`). Phase 13~15에서 화면별로 작성한 E2E를 5개 핵심 플로우 회귀 스위트로 묶고 **CI 야간 실행**한다(`docs/08 18.1.3`).
- **모바일:** Detox로 사용자 플로우 검증(`docs/08 §16 Phase 헤더·16.x AI 프롬프트`). 단, **Detox는 `docs/10 §5` 테스트 스택 표에 미수록**이다 🟡 **TBD(선정 필요)** — WBS는 Detox를 전제하나 기술 스택 SSOT(`docs/10`)에 등재되지 않았으므로, Detox 채택을 `docs/10 §5`에 확정 등재할 것을 권고한다. (대안 후보: Maestro. 둘 다 미확정.)
- **접근성 E2E:** 키보드 네비게이션은 Playwright 키보드 시나리오로 검증한다(`docs/14 §6-1`, `docs/08 17.3.1`).

### 2-4. RLS 정책 검증 — pgTAP ✅

- **도구:** pgTAP(`docs/10 §5`, `docs/08 18.1.4`). 본 절은 `docs/13 §6`을 테스트 전략에 통합한 것이다.
- **명세 출처:** `docs/13 §2` 정책 매트릭스의 각 **✅ 셀이 곧 pgTAP 테스트 케이스의 명세**다(`docs/13 §6`).
- **각 마이그레이션 직후 즉시 검증** — 스키마(컬럼·타입·제약·FK·enum)와 RLS 정책을 함께 검증, 테스트 없는 마이그레이션은 머지 금지(`docs/08 §1 Phase 헤더`).
- **확정 검증 매트릭스**(`docs/13 §6`):

| 검증 항목 | 기대 결과 | 근거 |
|---------|---------|------|
| `records` SELECT: 보호자/본인/권한자 | 허용 | `docs/13 §3.1` |
| `records` SELECT: 무권한자 | 0행 | `docs/13 §3.1` |
| `records` INSERT: write 미만 | 거부 | `docs/13 §3.1` |
| `records` UPDATE/DELETE: 만료 권한 | 거부 | `docs/13 §3.1` |
| `self_expressions` INSERT: 비본인 | 거부 | `docs/13 §3.2` |
| `self_expressions` UPDATE: 당일 외 | 거부 | `docs/13 §3.2` |
| `permissions` 변경: 비주보호자 | 거부 | `docs/13 §3.3` |
| `access_logs` UPDATE/DELETE | 거부(불변) | `docs/13 §4` |
| `permission_logs` UPDATE/DELETE | 거부(불변) | `docs/13 §4` |

- **전체 회귀:** Phase 11.5에서 모든 RLS 정책을 한 번에 회귀하는 pgTAP 마스터 스위트로 통합하고(`docs/08 11.5.2`), Phase 18에서 CI 회귀 잡으로 운영한다(`docs/08 18.1.4`). 스테이징 마이그레이션 검증에도 동일 스위트를 실행한다(`docs/08 19.1.3`).
- **TBD 8개 테이블:** `docs/13 §2`에서 🟡 TBD인 테이블(`users`·`guardian_persons`·`person_accounts`·`record_files`·`life_milestones`·`handovers`·`notifications`·`persons` 쓰기)은 정책 미정 상태에서 **"RLS enabled & 정책 0개 → 전체 거부"를 명시 테스트**로 두고, 정책 확정 시 케이스를 추가한다(`docs/13 §6` 말미).

### 2-5. 접근성 테스트 — axe-core · Lighthouse · 대비 측정기 ✅

- 본 절은 `docs/14 §6 검증 도구`를 테스트 전략에 통합한 것이다.
- **자동화**(`docs/14 §6-1`):

| 도구 | 검증 대상 | 매핑 |
|------|----------|------|
| **axe-core** | ARIA·시맨틱·대비 자동 스캔(위반 0건) | `docs/14 §6-1`, `docs/08 17.3.2·17.3.3` |

| **대비 측정기** | 토큰 조합 4.5:1(AA)/7:1(AAA) 수치 — Vitest 단위 계산 | `docs/14 §1-1`, `docs/08 12.1.4·17.3.3` |
| **Playwright** | 키보드 네비게이션 E2E | `docs/14 §6-1`, `docs/08 17.3.1·18.1.3` |

### 2-6. 시각 회귀 — Chromatic ⚪ (P1)

- **도구:** Chromatic(`docs/10 §5` ⚪ P1, `docs/08 18.1.5`). Phase 12 Storybook 기반으로 PR마다 컴포넌트 시각 diff를 검토한다(`docs/14 §6-1` "Chromatic 포커스·접근성 모드 시각 회귀").
- **P1 우선순위**이므로 MVP 차단 게이트에서는 제외하고, 차기 릴리스에서 도입한다.

### 2-7. 성능 테스트 — k6/Artillery 🟡

## 3. 커버리지 목표

### 3-1. 정량 목표

`docs/08 18.1.1`이 지정한 **핵심 로직 70%**를 기준선으로 하고, 보안·권한 도메인은 상향한다.

| 도메인 | 라인/브랜치 목표 | 사유 | 근거 |
|--------|:---:|------|------|
| 전역 핵심 로직 | **≥ 70%** | WBS 기준선 | `docs/08 18.1.1` |
| 인증·권한(Auth/Permissions) | **≥ 90%** | 보안 핵심·이중 검증 대상 | `docs/08 §4 Phase 헤더`, `docs/13 §3.3` |
| RLS 정책 | **확정 정책 100%** | `docs/13 §2` ✅ 셀 전수 | `docs/13 §6`, `docs/08 11.5.2` |
| 기록·자기표현 CRUD | ≥ 80% | 데이터 무결성·권한 분기 | `docs/13 §3.1·§3.2` |
| 응급정보·민감 파일 | ≥ 90% | PII·추가 인증(`docs/08 3.2.5·7.8`) | `docs/05 §11-2` |
| UI 컴포넌트 | 스냅샷 + 핵심 인터랙션 | 시각 회귀(P1)로 보완 | `docs/08 §12 Phase 헤더` |
| 접근성 토큰 대비 | 6 도메인 + 당사자 모드 전 조합 | 수치 자동 검증 | `docs/14 §1-1` |

### 3-2. 측정 방식

- Vitest 커버리지(c8)로 측정하고, **커버리지 70% 게이트를 CI(`docs/08 0.14`)에 추가**한다(`docs/08 18.1.1`). 미달 영역은 보강 테스트를 작성한다.
- RLS 커버리지는 라인 커버리지가 아니라 **`docs/13 §2` 매트릭스 ✅ 셀의 케이스 충족 여부**로 측정한다(정책 매트릭스 기반).
- 커버리지 수치(70/80/90)는 게이트 운영 기준일 뿐이며, 보안 도메인은 수치와 무관하게 §2-4 매트릭스 전수 검증을 별도 만족해야 한다.

## 4. E2E 핵심 시나리오 목록

### 4-1. P0 — 5개 핵심 플로우 (회귀 스위트 필수)

| # | 시나리오 | 원천 워크플로우 | 핵심 검증 | 우선순위 |

## 5. 테스트 데이터 & 픽스처 전략

### 5-1. 역할 7종 시드 사용자

`docs/13 §1 Enum(user_role)` 기준으로 픽스처를 구성한다.

| 픽스처 | role | 용도 |
|--------|------|------|
| `seed_guardian_primary` | guardian (is_primary=true) | 권한 부여/회수·매트릭스 관리 |
| `seed_guardian_co` | guardian (is_primary=false) | 일반 보호자 차단 검증(`docs/13 §3.3`) |
| `seed_person` | person (+ person_account) | 당사자 본인 자기표현·접근성 모드 |
| `seed_supporter` | supporter | 일지·인계(`docs/08 18.2.3`) |
| `seed_teacher` | teacher | IEP |
| `seed_social_worker` | social_worker | ISP·전환계획 |
| `seed_therapist` | therapist | 회기·평가 |

> 권한 부여/회수·만료 검증을 위해 **유효 권한·만료 권한·무권한** 3종 `permissions` 상태를 함께 시드한다(`docs/13 §1 has_permission` 유효기간 조건).

### 5-2. 민감정보 더미 (PII)

- `persons.emergency_info`(혈액형·알레르기·복약·비상연락, `docs/02 §3`)와 `record_files.is_sensitive=true`(진단서 등, `docs/05 §5`)는 **합성 더미 데이터만** 사용한다. 실 PII 금지.
- 민감 파일 추가 인증(`docs/08 7.8`)·응급정보 추가 인증(`docs/08 3.2.5`) 검증용 PIN/생체 통과·미통과 픽스처를 둔다.

### 5-3. 시드 데이터 & 격리 (RLS 다중 사용자)

- **RLS 테스트 격리:** pgTAP는 `SET LOCAL ROLE` + `auth.uid()` 컨텍스트 전환으로 역할별 세션을 분리한다(`docs/13 §6` 예시). 각 케이스는 `BEGIN ... ROLLBACK`으로 격리해 부작용을 남기지 않는다.
- **통합 테스트 격리:** Supertest는 실 Supabase에 시드 후 테스트별 트랜잭션 롤백 또는 케이스별 네임스페이스(고유 이메일/person)로 격리한다(`docs/08 11.5.1` "실 Supabase에 시드 데이터").
- **append-only 로그:** `access_logs`·`permission_logs`는 INSERT-only(`docs/13 §4`)이므로 정리(cleanup) 대신 테스트 DB 리셋으로 격리한다.
- **성능 시드:** 타임라인 10k 기록·권한자 20명 등 대량 시드는 별도 시드 스크립트로 생성한다(`docs/08 18.3.1·18.3.2`).

## 7. 경계면(API↔프론트 shape) 검증 방침

API 스펙(`docs/12`)과 프론트 연동부의 데이터 shape 불일치를 통합 단계에서 잡는 것이 본 절의 목적이다(원칙 P4).

- **단일 계약 소스:** API 요청/응답 JSON 스키마는 현재 미정이며 **구현 단계(Phase 4)에서 OpenAPI로 확정**한다(`docs/12 §13`). 확정 전까지 임의 스키마를 가정하지 않는다.
- **Zod 스키마 공유:** 폼·검증은 RHF+Zod이며 Zod 스키마는 `packages/shared`의 `validation` 패키지·JSONB 스키마와 공유된다(`docs/10 §1`, `docs/08 0.9`). **동일 Zod 스키마를 API 입력 검증과 프론트 폼 검증이 공유**함으로써 shape 정합성을 컴파일·런타임 양쪽에서 보장한다.
- **타입 안전:** TypeScript strict + Prisma 타입(`docs/10 §1·§3.2`)으로 DB↔서버 타입을 고정하고, shared 패키지 타입을 web·mobile이 재사용한다(`docs/08 0.9`).
- **통합 검증:** Supertest 통합 테스트가 실제 응답 body를 검증(필드·타입·상태코드)하며, 프론트는 동일 shape를 TanStack Query 훅으로 소비한다(`docs/10 §1`, `docs/08 §16 Phase 헤더` "웹과 동일 API를 TanStack Query 훅으로 재사용").
- **shared 패키지 import 검증:** `docs/08 0.9`가 shared 패키지 import 동작 검증 테스트를 지정 — 경계면 회귀의 토대.
- **공통 규약 TBD:** 인증 헤더·페이징 파라미터·에러 응답 형태·상태코드(`docs/12 §13`)는 OpenAPI 확정 후 계약 테스트(contract test) 대상으로 추가한다.
